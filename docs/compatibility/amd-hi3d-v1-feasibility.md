# Hi3D v1.0 feasibility for Modly AMD geometry refinement

25 October 2026. **NO-GO for a 512³ Hi3D compatibility/model trial on the current RX 9070 XT stack.** The released sparse-convolution backend is CUDA-specific; no maintained compatible gfx1201 backend was established. Stop rather than begin speculative kernel porting. Hi3D accepts our mesh format in principle, but hardware compatibility and wound preservation are separate, unresolved requirements.

Source assessment pinned to official [Hi3D commit 13657ad09afaa92e350b461a1cd66399e44a59c4](https://github.com/hi3d-official/Hi3Dv1.0/tree/13657ad09afaa92e350b461a1cd66399e44a59c4). No software, weights or kernels were installed, compiled or executed; no WSL launch, model import or asset modification occurred. Only this report is added to Modly.

## Dependencies and AMD blockers

The measured release requires Linux, Python 3.10.12, NVIDIA Ampere or newer, PyTorch 2.5.0+cu124, torchvision 0.20.0+cu124, CUDA 12.4.131, Triton 3.1.0, spconv-cu120 2.3.6, flash-attn 2.7.4.post1, transformers 4.46.3 and NumPy 1.26.4. Package Python is restricted to >=3.10,<3.11. Additional declared dependencies are safetensors >=0.4.3, huggingface-hub >=0.28,<1, Pillow >=10.3, trimesh >=4.4,<5, pyfqmr >=0.4 and Accelerate >=0.31,<2. These last packages are ranges, not a complete exact transitive lock. Background removal/rembg and Hunyuan coarse generation are optional. [Package metadata](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/pyproject.toml), [exact constraints](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/docker/constraints.txt), [verified installation](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/docs/installation.md).

Saved Modly evidence describes Python 3.12.3, Torch 2.9.1/ROCm 7.2.1, Triton 3.5.1 and gfx1201, with separately qualified FlexGEMM. That is a different stack; it must not be downgraded or treated as Hi3D-qualified. WSL was not launched to re-query it. [Existing runtime evidence](amd-wsl-rocdxg-gpu-resume.md), [native backend qualification](amd-wsl-flexgemm-native-import-resume.md).

## 512³ feasibility and memory

512³ is the only sensible initial target if the backend blocker is resolved. It runs one 64³-support pass, targeting at most 80,000 occupied support voxels, followed by three learned 2× decoder upsamplings. This is sparse extraction, not allocation of a dense 512³ tensor. 1024³ and 1536³ add passes and another transformer; neither is admitted by this assessment. [Pass implementation](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/pipelines/sparc3d_pipeline.py), [architecture](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/docs/pipeline.md).

Calculated scale indicators, **not measured peaks**: the licensed artifact schedule lists approximately 3.42 GiB per transformer and 0.35 GiB for VAE weights. For a hypothetical 80,000-row hidden sequence, one fp16 2,112-channel feature matrix is 0.315 GiB, packed QKV approximately 0.944 GiB, and an 8,448-channel MLP intermediate 1.259 GiB; actual attention rows depend on sparse I/O downsampling. Multiple buffers, sparse indices, decoder expansion, workspaces, image encoders and allocator overhead coexist. These numbers establish neither a 16 GB fit nor an out-of-memory result. [Weight sizes](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/LICENSE#schedule-2--licensed-asset-schedule), [transformer](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/models/transformers/sparc3d_transformer.py).

The release does not establish a 512³ peak for this card; its documented 1536³ validation used a 96 GB H20. Offload reduces model residency but materializes **both** transformers on CPU, about 7.20 GiB of core weight-file payload before the two fp32 encoders, loading copies and host overhead. It does not eliminate decoded-feature memory. The 12-million-row pipeline ceiling is checked after decoding and only when another pass follows; it is not a 512³ allocation guard. A separate residual-block guard can skip oversized blocks. Existing Modly RAM/VRAM limits must remain decisive; offload is not evidence that 32 GB host RAM is sufficient. [Offload and guards](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/pipelines/sparc3d_pipeline.py), [decoder block policy](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/models/autoencoders/blocks.py).

Implementation effort is high: sparse-backend equivalence plus attention/Triton qualification and new containment/provenance integration. A package import would prove almost nothing because dependencies are lazy. No defensible total memory or completion-time estimate exists for this unported path.

## Zombie input and likely quality consequences

The existing C PLY (325,074 vertices, 665,232 triangles; SHA-256 `a2d015fbcd54f6b1232674c0fef239040501629460ab177dcf826f4b34d3809d`) can be read as the external triangle input with `process=False`. Hi3D validates finite coordinates, triangle indices and extent, copies the arrays and does not require watertightness. A future wrapper can open an authenticated copy read-only and export elsewhere; the CLI itself does not prevent output-path collisions. Original A and C remain immutable. [Mesh CLI](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/demo/refine_mesh.py), [validation](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/sparcubes/postprocess.py).

Use C's original RGBA image, not its rendered mesh preview or old TRELLIS conditioning. Hi3D uses different white-background preparation and separate DINOv2-large/CLIP encoders. It resamples geometry from support and an image prior; it does not preserve existing triangles or recover missing wound walls deterministically. Initial 64³ voxelization, adaptive support reduction and single-view ambiguity can lose narrow finger gaps or cavity detail. Improved fingers/continuity are plausible, unproven benefits. The same 512³ label as Modly does not establish higher effective detail. [Conditioner](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/models/conditioners/image.py), [support construction](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/ops/voxelize.py).

Wound preservation is a specific risk: extraction unconditionally calls ear-clipping hole filling for detected boundary loops up to 10,000 edges. Final processing drops non-largest components below 0.5% of total faces, simplifies toward one million faces at 512³ and normalizes position/scale. No semantic wound mask distinguishes intentional openings from defects. A closed, fully represented cavity might survive, but capping its open boundary or removing a small meaningful fragment could merely conceal defects. Future evaluation would need registered matched views and wound/cavity measurements, not watertightness or defect counts alone. [Unconditional call](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/pipelines/sparc3d_pipeline.py#L495-L509), [hole filling](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/sparcubes/fill_hole.py), [postprocessing](https://github.com/hi3d-official/Hi3Dv1.0/blob/13657ad09afaa92e350b461a1cd66399e44a59c4/sparc3d/sparcubes/postprocess.py).

## Cheapest falsifiable future test

**Do not start it now.** Reconsider only when a maintained gfx1201-capable sparse backend implementing the required spconv semantics is identified, without changing Modly's environment. No such route was established here; a speculative replacement is the stop condition.

One separately authorised, isolated, weight-free kernel proof would run in fail-fast order:

1. A tiny sparse 3×3×3 submanifold convolution through Hi3D's actual wrapper, checking coordinate order and fp32/fp16 outputs against an independent CPU calculation. Missing backend or required porting ends the proof immediately.
2. Actual packed variable-length self/cross attention with the transformer's 22 heads/head dimension 96 and the decoder's configured patch layout; compare with a small CPU attention reference.
3. The unmodified Triton voxelizer on a tiny synthetic triangle mesh and FlexiCubes on a known signed field; check coverage, finite positions and face orientation.

Use existing owned-process, RAM/VRAM, disk, deadline and cleanup safeguards; preserve the 22 GiB admission/final neural reservation guards, preferred-only 24 GiB and 12 GiB live floor. No Hi3D weights, zombie geometry or neural attempt are needed for this kernel proof. One failure means stop: no backend sweep, source-build campaign or automatic fallback. Passing kernels would justify a separately reviewed 512³ memory/quality proposal, not automatic model execution. 1024³/1536³ and production integration remain NO-GO.
